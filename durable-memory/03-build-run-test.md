# Build, run, test

## Install story (users)

Users never install lmgh and never need Go. The `_lmcode_` block names the
host (`cli="lmgh"`) and the script runs it with `run_lmcode`. The host is
found on `PATH` or fetched with `lmscript install github:lmctl-ai/lmgh`, which
downloads the release asset `lmgh-OS-ARCH` (OS: linux/macos/windows; arch:
x64/arm64; `.exe` on windows) into its tool cache
(`LMSCRIPT_TOOL_CACHE` or `~/.cache/lmscript/tools`), verifies sha256 against
`SHA256SUMS`; the compiler uses the binary's embedded schema. The only user prerequisite is `gh` itself (>= 2.45.0 < 3.0.0) with
`gh` auth; `LMGH_GH` overrides the gh path.

Releases: pushing a `v*` tag publishes automatically — CI runs `./test.sh`
and, once tests pass, the release job cross-builds the six assets +
SHA256SUMS, verifies the tag matches `lmgh --version`, and creates the GitHub
release. `scripts/release.sh <version>` (no `v` prefix) remains as the local
fallback: it builds the six assets + SHA256SUMS and creates the release; the
`version` constant in host.go must match the requested version.

## Build (developers)

```sh
CGO_ENABLED=0 go build -trimpath -ldflags='-buildid=' -o build/lmgh .
```

Go 1.26; dependencies `github.com/lmctl-ai/lmcode-go` and
`github.com/pelletier/go-toml/v2` (pinned in `go.mod`/`go.sum`; the SDK is the
same pseudo-version as lmcode-go-sample, which defines the result protocol).

## CLI protocol

- `lmgh --version` → `lmgh 0.2.2`
- `lmgh --lmcode-schema [--json]` → the embedded schema bytes (byte-equal to
  `schema/lmgh.dsl.json`; bytecode is bound to the sha256 of these bytes)
- `lmgh --lmcode-signatures` → registry signatures (full SDK std + host; a
  superset of what the compiler exposes)
- `lmgh [--lmcode|--first|--last] FILE ...` → load + run each file in one
  shared host (first roles before normal, last after). Exactly one terminal
  frame is written, `LMCODE_RETURN_BEGIN\n<envelope>\nLMCODE_RETURN_END\n`;
  `lmscript`'s `run_lmcode` parses it. Success is `{"ok":true,"result":null}`;
  failures carry phase/code/message/line/column.
- anything else → a `CLI_USAGE` failure frame, exit 2

Exit codes: 0 ok · 2 usage · 3 load/VM/host errors · 4 `APP_FAIL`
(`Report.fail_if_any` with findings, unreadable bytecode file). These are
the host's exit codes; each example script maps the `run_lmcode` result onto
the same codes (`APP_FAIL` → 4, any other failure → 3).

## Parity rule

The compiler-visible catalog (`lmscript --lmcode-signatures
schema/lmgh.dsl.json`, implicit std + host) must be a subset of the host
registry (`lmgh --lmcode-signatures`) — checked both directions for host
signatures in `test.sh`. The registry is intentionally a superset (full SDK
std v3) so every compiler-emittable call binds.

## Test flow (`./test.sh`, 85 checks)

1. compiler present (`LMSCRIPT_BIN` overrides)
2. `scripts/sync-cli.sh --verify` (auto-syncs when missing)
3. `go build`, then a `gh` wrapper on `PATH` pointing at
   [tests/fake-gh.py](../tests/fake-gh.py) — canned JSON, fails for any repo
   other than `octo/demo`, never touches the network
4. examples run as scripts (`lmscript examples/NAME.lms`), and stdout + report files diff
   byte-for-byte against `tests/expected/`
5. refusal chunks: bad state/limit/merge-kind, list `at()` out of range,
   unknown repo, missing gh (`LMGH_GH` pointing nowhere), live + dry-run
   writes, `APP_FAIL`, junk bytecode, missing bytecode file

Expected outputs are pinned and never regenerated by the test run itself.

## Native host flags

The host accepts only the lmcode flag family. Full-gate controls prove retired-option refusal, exact schema/signature output and new execution dispatch; missing files retain application-failure exit 4. Compiler selection only checks that a candidate `lmscript` accepts an `_lmcode_` program against a host-only schema (`--check`); versions and bytecode format are not inspected. `savedsl` and `out=` no longer exist: scripts execute programs with `run_lmcode`.
